## D1. §8.4 severity 公式缺星级字段（已修）

### 问题

规格 §8.4 的痛点优先级公式需要按星级拆分负面提及数：

```
severity = (1星负面提及数 × 1.0 + 2星负面提及数 × 0.8 + 3星负面提及数 × 0.5) / neg_count
```

但两处都没有星级：

| 位置 | 规格原文列出的字段 | 有 score 吗 |
|---|---|---|
| §8.2 aspects 输出 | `review_id, product_id, aspect_name, sentiment, confidence, evidence_text, create_time` | ❌ |
| §7.1 `review_aspects` DDL | 同上 | ❌ |

即 Job 04 拿不到星级，公式无法计算。

### 处理

采用方案 A（加字段）：

1. `review_aspects` 表增加 `score TINYINT`（位于 `sentiment` 之后），已应用到线上表
2. `sql/schema.sql` 同步更新
3. **Job 02 的输出必须包含 `score` 字段**（从 cleaned 数据带下来）

采用方案 B（Job 04 回 join cleaned Parquet）也可以，但每次算优先级都要重读一份大数据，
且 join 键只有 `review_id`，不如直接把星级带到明细表里省事。

### 影响

- `review_aspects` 从 9 列变 10 列
- Job 02 输出结构：`review_id, product_id, aspect_name, sentiment, score, confidence, evidence_text, create_time`
- Job 03 写 `review_aspects` 时要带上 `score`

## D2. §5 京东评论接口已不可直接访问（方案调整）

### 问题

规格 §5.1 写的是"主力：京东商品评论公开接口形态"。2026-11-02 实测：

| 目标 | 结果 |
|---|---|
| `https://www.jd.com` | HTTP 200 |
| `https://item.jd.com/100012043978.html` | HTTP 200，但返回反爬占位页 |
| `https://api.m.jd.com/`（pc_club_productPageComments） | **HTTP 403** |
| `https://club.jd.com/comment/productPageComments.action` | **HTTP 444 The Request Forbidden** |

京东已要求 `h5st` 签名 + 登录态 cookie，匿名请求一律拒绝。这不是实现问题，是入口关闭。

### 处理

采集器设计成 **provider 可切换**：

```python
# crawler/jd_review_crawler.py
def collect(product_id, provider="jd"): ...
#   provider="jd"    -> 真实接口（需 cookie / 签名，依赖外部凭证）
#   provider="local" -> 读取现成 JSONL 或公开数据集
#   provider="mock"  -> 按 config/aspects.yaml 合成评论，条数可控
```

JSONL 输出结构（§5.3）与 provider 无关，所以 **Job 01–04 完全不用改**，
后续拿到真实数据只需换 provider。

`source` 字段记录真实来源（`jd` / `local` / `mock`），便于区分和答辩说明。

### 待定

真实京东通道是否可用，取决于能否拿到有效登录 cookie。若不可用，
交付时使用 `mock` 或公开数据集，并在 README 中说明数据来源。

## D5. 规格里的示例 SKU 实测是白酒商品，不是手机（**待用户提供新 SKU**）

### 问题

规格 §5.2 / §7 用 `100012043978`（品牌A A1，手机）作为示例产品。
2026-11-02 用真实京东接口验证该 SKU，返回的评论是：

> "25年的飞天买来送人，京东溯源，i茅台溯源都用上了，没问题，安全下车。"
> "不愧是国酒茅台，酒花饱满圆润，挂杯明显，轻抿一口，醇厚丰满诸位协调。"
> "口粮茅台还是要喝一年以上的，所以我今年开始一直选25年的，已经买了7箱了。"

语义标签为「口感香浓」「酱香浓郁悠长」「酒体晶莹透亮」，
`wareAttribute` 为「颜色: 2025年 / 型号: 单瓶装」，
`maidianInfo` 含 `9435_100012043978_全部_...` 证实页面 SKU 即 `100012043978`。

**结论：该 SKU 是飞天茅台白酒，与规格设想的手机品类不符。**

同理 `100026667910` 也未经验证，不能假定为手机竞品。

现有 7 个属性（电池续航、影像拍照、屏幕显示、做工质感、物流配送、客服服务、性价比）

## D7. 京东风控实测结论（2026-11-02）

### 逐层排查结果

| 层 | 尝试 | 结果 |
|---|---|---|
| 1 | PC 详情页 `item.jd.com` | 反爬占位页（35 KB，标题是通用首页标题） |
| 2 | 手机版 `item.m.jd.com` | ✅ 正常渲染（250 KB，商品信息完整） |
| 3 | 直接调评论接口 | `comment_getCommentList` 在 JS 的 `paramsAddSignApis` 签名名单内，调用返回 `{"code":"1","echo":"no access"}` |
| 4 | 无头 Chromium 加载 m 版页面 | 评论接口返回 `{"code":601,"msg":"活动太火爆了…"}`（风控） |
| 5 | Xvfb + 有头 Chromium 加载 PC 页 | 直接跳转 `pc-frequent-pro.pf.jd.com/?from=pc_item&reason=403`（**IP 级频控**） |

### 关键结论

1. **签名由浏览器 JS 自动完成**，不需要人工复制 cURL；
   但 `ParamsSign` 类混淆严重，纯 Python 复现不现实。
2. **当前这台机器的公网 IP 已被京东频控**。探测过程中的多次请求触发了限制，
   PC 端已被打到 403 频控页，手机端评论接口返回 601。
   这是 IP 级限制，与代码无关，需要时间衰减。

### ⚠️ 更严重的业务问题：目标商品尚无评价

用户指定的目标商品 `100433292168`（小米 Redmi K100）页面显示：

- 商品状态：「采购中预计 2026-11-13 日后有货」
- 评价区：`<P class="cmt_none_tips">暂无评价，欢迎您购买之后留下宝贵的评价</P>`

即该机型是**未正式开售的新品，一条评论都没有**，
无论反爬是否绕过，都采不到规格 §13 T2 要求的「每产品 ≥500 条」。

**因此必须换成已上市、已有大量评价的机型。**

### 后续可选路径

| 方案 | 可行性 | 说明 |
|---|---|---|
| A. 换成熟机型 + 等风控衰减 | 高 | 风控通常数小时到数天衰减，换 IP 或等待后重试 |
| B. 注入用户浏览器 cookie 后重试 | 中 | 签名由页面 JS 算，cookie 可提供信任度 |

## D8. §8 四个作业实现完成 + 踩到的三个坑

2026-11-02 完成 `spark_jobs/01_clean.py`、`02_absa_extract.py`、`03_aggregate.py`、
`04_priority_gap.py`，以及 `absa/model_adapter.py`、`absa/rule_fallback.py`。
用 mock 数据（1000 条）实测全流程 **59 秒跑通**，MySQL 六张表均有数据。

### 坑 1：WSL 空闲即关机 → HDFS safe mode 反复发作

WSL 发行版空闲约 15 秒就停机，下次调用时 HDFS 重新启动，
NameNode 每次都要进 safe mode（约 8 秒）。作业算完准备写盘时撞上就整个失败，
排查过程中连续失败 3 次。

**解决：** 新增 `hdfs_util.py`，提供 `wait_hdfs_writable()` 与带重试的
`write_parquet()`。所有作业统一走它写盘，`upload_to_hdfs.sh` 与
`run_pipeline.sh` 也补了等待逻辑。

### 坑 2：分区目录名是数字，Spark 把 `product_id` 推断成 bigint

`/spike/staging/cleaned/product_id=100215674663/` 这种 Hive 风格分区，
Spark 读回来时按目录名推断类型，数值型 ID 就变成了 `bigint`，
与 MySQL 里的 `VARCHAR` 对不上，join 时被隐式转换、极易出错。

**解决：** 读完立刻 `withColumn("product_id", col("product_id").cast("string"))`。

### 坑 3：Spark 的 `avg()` 不接受 BOOLEAN

`F.avg(F.col("sentiment") == "positive")` 会抛
`DATATYPE_MISMATCH: Parameter 1 requires NUMERIC`。

**解决：** 先 `F.when(cond, 1.0).otherwise(0.0)` 再 `avg()`。

### 其他实现决策

- **Job 02 主路径未启用**：`torch` / `transformers` 未安装，
  `model_adapter.py` 检测不到 `SPIKE_ABSA_MODEL` 环境变量时自动降级到规则路径。
  接口已按 §8.2 固定，装上模型后设一个环境变量即可切换，无需改作业代码。
- **情感词典扩充**：原词典仅 10 正 / 10 负，「表现不错」「给力」「推荐」
  都识别不到，导致正面率只有 0.42（mock 实际是 62%）。扩充到 29 正 / 29 负，
  并加了「太 / 超 / 略」三个程度词后，正面率回到 0.64，与数据分布吻合。
- **分句粒度**：情感判断先按逗号切分句，避免
  「物流很快，但是客服态度差」被整句话判成同一个极性。
- **`review_aspects.score`**：§8.4 的 severity 公式需要星级分布，
  见 D1，该列已加入表结构和 Job 03 输出。

## D9：§10 后端 / §11 前端的实现说明

**规模**：后端 9 个接口（规格要求 8 个，多一个 `/api/meta/aspects` 给前端做筛选下拉），
前端 3 个视图，全部实现并联调通过。后端 12 项自测全绿，前端三页无 JS 报错。

### 与规格的差异

1. **`/api/evidence` 返回的是证据片段，不是完整评论正文。**
   §10 说「原始评论证据」，但 MySQL 里只落 `review_aspects.evidence_text`
   （§9.3 定义的 ≤200 字原话片段），完整正文在 HDFS 的 cleaned parquet 里。
   为了不让后端去读 HDFS（会引入 Hadoop 依赖、拖慢响应），
   接口直接返回 `evidence_text`。它本来就是按「引用用户原话」设计的，够用。

2. **`/api/meta/aspects` 是额外接口**，规格 §10 没有。
   前端做属性筛选需要属性字典，加一个只读接口比硬编码更干净。

3. **优势判定阈值为正面率 ≥ 0.75、痛点 ≥ 0.30（提及量 ≥ 5）。**
   当前 mock 数据下目标产品正面率最高只有 0.74 左右（物流配送），
   达不到 0.75 的优势线，所以「优势」为 0 项。这是数据结论，不是 bug；
   前端对空列表有明确提示「没有明显长板，也没有致命短板」。
   真实数据接入后阈值不变，结果会随数据变化。

4. **`aspect_dictionary` 没有 `description` 列**，只有 `synonyms`。
   元接口按实际表结构返回 `aspect_name / category / synonyms`。

### 工程上的坑

5. **`/mnt/d` 是 DrvFs，不支持 chmod**，`npm install` 会在给
   `node_modules/**/bin/*.js` 加执行位时报 `EPERM`。
   解决：`npm install --no-bin-links`，然后直接
   `node node_modules/vite/bin/vite.js build`（不走 `npx` / `.bin` 符号链接）。

6. **`pkill -f "backend.app"` 会杀掉自己**：`bash -c` 的整条命令行里就包含这个字符串，
   `pkill -f` 匹配全命令行 → 自杀，表现为「命令执行了但完全没有输出」。
   解决：改成按 PID 文件管理（`scripts/run_backend.sh`），
   确实需要用 `pkill -f` 时用方括号写法 `[b]ackend.app` 规避自匹配。

7. **ECharts 全量引入，包体 1.15 MB（gzip 387 KB）**。
   演示够用；要优化可改成按需引入 `echarts/core` + 具体图表类型。

8. **数据源以好评为主时，痛点阈值无人达标 → 增加「相对短板」退化逻辑**。
   交付的真实数据 500 条里有 489 条是 5 星，全部属性的负面率只有 2.5%–4.3%，
   按规格 §8.4「负面率 ≥ 30% 判为痛点」会得到 **0 个痛点**，页面空着没有信息量。

   处理方式：**不改变规格的判定逻辑和入库标签**（`aspect_priority.label` 仍然按阈值算，
   该是 0 就是 0），只在 `/api/products/<id>/painpoints` 接口层做退化——
   当没有属性达到阈值时，按负面率排序返回前 3 个，并带上
   `fallback: true` 和一段说明文字；前端把标题改成「相对短板」并显示橙色提示条。

   这样做的理由：阈值判定是「有没有真痛点」，相对排序是「哪个短板相对最差」，
   两者语义不同，混在一张表里会误导；单独标出来、说清楚，比留个空页面有用。

### 验证结果

| 项目 | 结果 |
|---|---|
| 后端接口自测 `scripts/test_api.py` | **12/12 通过** |
| 验收测试 `scripts/acceptance_test.py` | **T1–T10 全部通过，53.3 秒** |
| 前端三个页面（headless Chromium） | **无 JS 报错** |
| 健康总览 | 5 个 KPI、7 行属性明细、2 个图表；覆盖 566 条评论，整体正面率 77.0% |
| 优势与痛点 | **6 个优势 / 1 个痛点**（客服服务，负面率 33.3%），证据展开 8 条并正常收起 |
| 竞品差距 | 7 个共同属性，领先 0 / 落后 2，最大优势 客服服务 +1.5pp，最大短板 影像拍照 −8.5pp |

> 这是补齐差评样本后的结果。在此之前只有好评，痛点 0 个、需要走 D9-8 的「相对短板」降级。

## D11. 竞品由 nova 16 SE 改为 nova 14（2026-11-04）

### 问题

补充交付的华为数据是 **nova 14（SKU 100224796932）**，
而 `config/products.yaml` 里原定的竞品是 **nova 16 SE（SKU 100300314335）**。
两个不是同一台机器，不能混用。

### 为什么必须换，而不是只补小米差评

只把小米的 200 条差评合并进来、竞品仍保持 500 条纯好评的话：

| | 只有好评 | 只加小米差评 |
|---|---|---|
| 小米 正面率 | 83.8% | 77.1% |
| 竞品 正面率 | 88.9% | 88.9%（不变） |
| 双方差距 | −5.1pp | **−11.8pp** |

差距凭空翻倍，纯粹因为竞品没有负面样本 —— 这是数据不平衡造成的伪结论，不能用。

交付的 nova 14 恰好是 **500 好评 + 200 差评**，和小米补齐后完全同构：

| | 小米 REDMI K90 | 华为 nova 14 |
|---|---|---|
| 好评 / 差评 | 500 / 200 | 500 / 200 |
| 属性提及 | 1316 | 998 |
| 正面率 | 77.1% | 79.4% |
| 负面率 | 7.1% | 7.2% |

所以把竞品换成 nova 14，对比才成立。

### 处理

1. `config/products.yaml`：竞品改为 `100224796932` 华为 nova 14
2. `sql/schema.sql`：同步更新种子数据，并把 `100300314335` 加进清理列表
3. MySQL `products` 表同步（job 04 读这张表来区分目标/竞品）
4. nova 16 SE 的 500 条数据归档到
   `data/incoming/2026-11-04/_retired-100300314335-nova16se.jsonl`（没删，可回滚）
5. `scripts/upload_to_hdfs.sh` 增加**清理 HDFS 上已移除商品目录**的逻辑。
   不清理的话 `/spike/raw/reviews/product_id=100300314335` 会一直留着，
   下游 Spark 仍会把它读进来，分析里会冒出已经下线的产品。

### 影响

- 交付物里「竞品」这一称谓从 nova 16 SE 变为 nova 14，README / 交接说明 / 交接表已同步
- 若日后拿到 nova 16 SE 的差评，把 `products.yaml` 改回去、重跑 `refresh_all.sh` 即可

## 二、交付什么

**两个 JSONL 文件**，文件名必须严格等于 SKU 号：

```
100215674663.jsonl      ← 小米 REDMI K90 的 500+ 条评论
100300314335.jsonl      ← 华为 nova 16 SE 的 500+ 条评论
```

打成一个压缩包发回即可。

### 文件格式硬性要求

| 要求 | 说明 |
|---|---|
| 编码 | **UTF-8无 BOM** |
| 格式 | **JSONL**：一行一条 JSON，行之间用 `\n` 分隔 |
| ❌ 不要 | 不要包成 `[{...},{...}]` 这种 JSON 数组 |
| ❌ 不要 | 不要多个 JSON 挤在一行 |
| ❌ 不要 | 不要加注释、不要留空行 |

正确示例（文件开头三行）：

```
{"review_id": "24859021747", "product_id": "100215674663", "brand": "小米", "model": "REDMI K90", "is_target": true, "score": 5, "content": "外观：质感确实相比以前的小米提升很大，特别是选的白色，看起来很好看不像中端机的样子。", "create_time": "2025-10-29 15:57:33", "source": "jd", "crawl_time": "2026-11-02 18:41:52"}
{"review_id": "24859012883", "product_id": "100215674663", "brand": "小米", "model": "REDMI K90", "is_target": true, "score": 5, "content": "到手红米K90体验很均衡！7100mAh大电池续航真的惊喜，日常通勤一天重度使用不用频繁充电。", "create_time": "2025-10-29 12:03:11", "source": "jd", "crawl_time": "2026-11-02 18:41:52"}
{"review_id": "24858991204", "product_id": "100215674663", "brand": "小米", "model": "REDMI K90", "is_target": true, "score": 4, "content": "屏幕素质不错，就是这个价位了还没给无线充电有点可惜。", "create_time": "2025-10-29 09:47:20", "source": "jd", "crawl_time": "2026-11-02 18:41:52"}
```

## 三、字段定义（一共 10 个，一个都不能少，也不要多加）

| 字段 | 类型 | 必填 | 说明 | 示例 |
|---|---|---|---|---|
| `review_id` | string | ✅ | 评论的唯一 ID，**用于去重，不能重复** | `"24859021747"` |
| `product_id` | string | ✅ | 商品 SKU，**必须用上表给的那两个值之一** | `"100215674663"` |
| `brand` | string | ✅ | 品牌，照上表填 | `"小米"` |
| `model` | string | ✅ | 型号，照上表填 | `"REDMI K90"` |
| `is_target` | **bool** | ✅ | 本方产品填 `true`，竞品填 `false`。注意是 JSON 布尔，不是字符串 | `true` |
| `score` | **int** | ✅ | 星级评分，整数 1–5。不是字符串、不带引号 | `5` |
| `content` | string | ✅ | **评论正文原文**，不改写、不截断、不翻译、不删标点 | `"外观：质感确实相比…"` |
| `create_time` | string | ✅ | 评论发表时间，格式 **`YYYY-MM-DD HH:MM:SS`** | `"2025-10-29 15:57:33"` |
| `source` | string | ✅ | 数据来源标识，填 `"jd"`；从别处获得的填对应来源 | `"jd"` |
| `crawl_time` | string | ✅ | 你采集这条数据的时间，格式同 `create_time` | `"2026-11-02 18:41:52"` |

### 几个容易错的点

1. **`product_id` 用我们指定的 SKU，不要用评论里自带的 `productId`/`referenceId`**
   京东评论里那个字段是**子 SKU**（比如「白色 12GB+256GB」是一个独立 SKU），
   如果用它，同一个商品的评论会被拆成几十份，统计就废了。**统一填表里给的那个 8 位 SKU。**

2. **`score` 必须是数字**，`5` 而不是 `"5"`；`is_target` 必须是布尔，`true` 而不是 `"true"`

3. **`content` 保留原文**
   包括表情符号、错别字、换行都保留（换行在 JSON 里写成 `\n` 转义）。
   不要用「清洗后的文本」，清洗是我们的下游作业在做。

4. **`review_id` 全局唯一**
   同一条评论不要重复写入。如果采集过程中翻页有重叠，请按 `review_id` 去重。

5. **数量不够可以凑**
   如果某个商品确实凑不满 500 条，有多少给多少，并在回复里说明实际条数。

## 四、交付前自检

项目里有个校验脚本，你可以拿它检查自己的文件（如果拿不到脚本，按上面的要求人工核对也行）：

```bash
python crawler/validate_jsonl.py 100215674663.jsonl 100300314335.jsonl
```

它会检查：
- 每行是否是合法 JSON
- 10 个字段是否齐全、有没有多余字段
- 字段类型对不对（`score` 是数字、`is_target` 是布尔）
- `product_id` / `brand` / `model` / `is_target` 是否和上表一致
- `create_time`、`crawl_time` 的时间格式
- `review_id` 有没有重复
- 每个文件的实际条数

全部通过会打印 `✅ 校验通过`。

## 五、参考信息：京东评论接口（如果你想自己抓）

如果打算用程序抓，下面这些能省不少时间。**如果打算手工整理，可以跳过。**

### 可用端点

```
GET https://club.jd.com/comment/skuProductPageComments.action
    ?callback=fetchJSON_comment98
    &productId=100215674663
    &score=0
    &sortType=5
    &page=0
    &pageSize=10
    &isShadowSku=0
    &fold=1
```

返回 JSONP：`fetchJSON_comment98({...})`，剥掉外层就是 JSON。

### 关键注意事项

| 事项 | 说明 |
|---|---|
| **是 `skuProductPageComments`** | 不是 `productPageComments`。后者现在恒返回 `{}`，一字之差 |
| **必须带登录 Cookie** | 没有登录态会返回 `601 活动太火爆了`。Cookie 从浏览器 F12 → Network → Request Headers 里复制 |
| **`sortType=5`** | 推荐排序，`maxPage` 一般是 100（即 1000 条）。`sortType=6`（时间排序）`maxPage` 只有 2，拿不到足够数据 |
| **限流极其严格** | 实测连续请求 2 页就会被封，返回纯文本「活动太火爆，请稍微再试」。被封后静默 90 秒仍然 8/8 拒绝，响应 0.1 秒（WAF 直拒）。**建议页间隔 ≥ 30 秒**，被封就等 10 分钟重试 |
| **建议断点续传** | 每采到一页立即追加写文件，用状态文件记页码，避免被封后前功尽弃 |

### 返回字段对应关系

| 我们要的字段 | 接口里的字段 |
|---|---|
| `review_id` | `id` 或 `idStr` |
| `score` | `score`（已是数字） |
| `content` | `content` |
| `create_time` | `creationTime`（已是 `YYYY-MM-DD HH:MM:SS`） |

其余字段（`brand` / `model` / `is_target`）按第一节的表格固定填入。

## 六、补充要求：请务必带上差评和中性评价

> ✅ **2026-11-04 已完成**：已收到小米差评 200 条、华为 nova 14 好评 500 + 差评 200 条，
> 两边各 700 条、结构对称，痛点分析已经跑出结果（客服服务负面率 33%，判为痛点）。
> 本节保留作为后续补采的要求说明。

⚠️ **这一节很重要，不做的话数据基本没用。**

第一批交付的数据格式完全正确、也确实抓到了 500 条，但**500 条里有 489 条是 5 星好评**，
1 星和 2 星一条都没有。结果就是我们的痛点分析全部落空——

所有 7 个属性的负面率只有 **2.5%–4.3%**，而规格要求「负面率 ≥ 30% 才算痛点」，
最后算出来 **0 个痛点**，整个「发现用户不满」的功能就废了。

### 怎么补

接口的 `score` 参数就是星级过滤，抓的时候**分开抓**：

| `score` | 含义 | 建议条数 |
|---|---|---|
| `1` | 差评（1–2 星） | **每个商品 ≥ 200 条**，有多少抓多少 |
| `2` | 中评（3 星） | 每个商品 ≥ 100 条 |
| `3` | 一般（4 星） | 可选 |

请求示例（只改 `score`，其余和之前一样）：

```
https://club.jd.com/comment/skuProductPageComments.action
  ?callback=fetchJSON_comment98
  &productId=100215674663
  &score=1          ← 差评
  &sortType=5
  &page=0
  &pageSize=10
  &isShadowSku=0&fold=1
```

### 交付方式

**不用合并到一个文件**，分文件给我就行，我这边按 `review_id` 去重合并：

```
100215674663.jsonl          ← 已有的 500 条好评
100215674663.diff.jsonl     ← 新抓的差评/中评
100300314335.jsonl
100300314335.diff.jsonl
```

字段格式和第五节完全一致，`score` 字段如实填接口返回的星级（1–5 的数字）。

### 如果用的是我们的脚本

已经把 `--score` 加上了，直接跑：

```bash
# 抓差评，每个商品 200 条
python crawler/jd_slow_crawl.py --score 1 --target 200 --review-interval 12

# 抓中评
python crawler/jd_slow_crawl.py --score 2 --target 100 --review-interval 12
```

结果会追加到同一个 `data/raw/<sku>.jsonl`，按 `review_id` 自动去重，
进度文件按星级分开存，互不覆盖。

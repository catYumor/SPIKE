### 1.1 可用性口径（重要，别误判）

**HDFS 的可用性 = WSL 发行版的可用性。** 实测：

- 发行版一启动，`@reboot` 看门狗在 **约 1 秒**内拉起进程；
- 但 **完全健康（safemode OFF）需要 25—35 秒**；这期间 `hdfs dfsadmin -safemode get`
  返回 `ON`、`Configured Capacity: 0`、`Live datanodes` 可能为 0。
  **在发行版启动后 30 秒内做验收检查会误判为失败。**
- WSL 2.6.1 在**最后一个 `wsl.exe` 客户端断开约 15 秒后**把发行版置为 `Stopped`，
  即使里面还有 HDFS 进程在跑。因此 **HDFS 不是 7×24 常驻**：
  没有人使用 WSL 时它会被一起停掉，下次使用时自动恢复。
  （已验证 `.wslconfig` 的 `vmIdleTimeout=86400000` **无法**阻止该行为，已回滚。）

恢复时间指标：**进程 ≤60 秒、完全健康 ≤90 秒**（发行版启动场景下实际为 ~1 秒 / ~25—35 秒）。

若确实需要 7×24 常驻，办法是**保持一个 WSL 客户端附着**，例如在另一个 Windows 终端里执行：

```powershell
wsl -d Ubuntu -u hadoop -- sleep infinity
```

该进程存活期间发行版不会被回收，HDFS 也就持续在线。

## 4. 常驻机制：cron 看门狗

crontab（用户 hadoop）：

```cron
@reboot /home/hadoop/spike-hdfs-boot.sh >> /home/hadoop/logs/spike-hdfs-cron.log 2>&1
* * * * * /home/hadoop/spike-hdfs-boot.sh >> /home/hadoop/logs/spike-hdfs-cron.log 2>&1
```

`spike-hdfs-boot.sh` 的行为：

1. `flock` 防重入，且**子进程用 `9>&-` 关闭继承的锁 fd**（见 6.4，这是修过的 bug）；
2. 先看**进程是否存在**（`pgrep -f proc_namenode`），再看**端口是否监听**，两者都不满足才启动，
   避免把「正在启动中」的守护进程重复拉起；
3. 按 NameNode → DataNode → SecondaryNameNode 顺序启动；
4. 每次运行打印 `状态: nn=.. dn=.. snn=..` 便于巡检；健康时只打印一行、不做任何动作。

## 6. 关键坑（都踩过）

### 6.1 `wsl.exe <命令>` 启动的进程会在命令结束时被杀

通过 `wsl.exe -d Ubuntu -u hadoop -- bash -c '...'` 启动的进程，cgroup 为 `0::/init.scope`；
命令返回后该 scope 被回收，HDFS 守护进程随之被杀。

### 6.2 用户级 systemd 单元方案不可靠

试过 `systemd-run --user` 与 `~/.config/systemd/user/spike-*.service` + `loginctl enable-linger`：

- linger 可免密开启；
- 但 `user@1001.service` 会以 **`Result: resources`** 失败并反复重启，
  `systemctl --user` 频繁报 `Failed to connect to user scope bus via local transport`；
- `dmesg` 显示 **WSL interop 层直接管理该用户会话**：
  `WSL (2 - Interop) ERROR: operator():2721: systemctl is-active user@1001.service returned: failed`。

结论：**该用户会话的生死由 WSL interop 决定，不适合承载常驻服务。**
相关 unit 文件已删除，linger 已关闭。

### 6.3 cron 的 cgroup 是可靠的落点

`cron.service` 的 cgroup 为 `/system.slice/cron.service`，与 `/init.scope` 和用户会话都无关，
因此由 cron 启动的守护进程能在 `wsl.exe` 调用结束后继续存活（在发行版存活期间）。

### 6.4 `flock` 会被 `nohup ... &` 的子进程继承

第一版看门狗写成 `exec 9>lock; flock -n 9; ... nohup cmd &`，**后台子进程继承了 fd 9**，
锁在守护进程存活期间永不释放，看门狗此后每分钟只打印「上一次启动仍在进行，跳过」而彻底失效
（13:38—13:40 连续三次）。修复：子进程重定向 `9>&-`。

### 6.5 活跃日志不在 `$HADOOP_HOME/logs`

看门狗用 `nohup hdfs namenode`（前台模式，输出到 console）启动，日志被重定向到
`/home/hadoop/logs/hdfs-{namenode,datanode,secondarynamenode}.log`。
而 `/usr/local/hadoop/logs/hadoop-hadoop-*.log` 是早期用 `start-dfs.sh` 启动时留下的**陈旧文件**
（停留在 13:19），排查看前者。

## 7. 环境生命周期（经独立复核修正）

初版把现象描述为「核心 systemd 服务（含 cron）自发重启」，**这是错的**。实测根因是：

- `wsl.exe -l -v` 在两次调用之间直接返回 **`Ubuntu Stopped`**；
- 每次调用若发行版处于 Stopped，就是**一次全新的发行版启动**：PID 1 启动时间、`boot_id`、
  `/proc/uptime` 全部重置；
- 有时内核并不重启（`/proc/uptime` 与 `boot_id` 保持），只是发行版/PID 命名空间重建——
  两种情况都会杀掉 cron 与全部 HDFS 进程，随后由 `@reboot` 看门狗拉起。

反证：在**一次连续 165 秒的会话内**（期间无新的 `wsl.exe` 调用），cron PID 与 3 个 HDFS PID
全程不变、`etimes` 单调增长、**零重启**，每分钟只有一行心跳日志——不存在服务自发 flapping。

**不存在需要修复的「服务抖动」缺陷**，需要理解的是「发行版随客户端存在」这一生命周期。

另：WSL 内 `load average` 长期显示 12—14，但 `vmstat` 显示 `r=0 b=0`、CPU 100% idle，
属 **WSL2 负载统计假象**，不是真实争用。

## 9. 若要更彻底的方案（需 root）

若愿意提供 sudo 密码，可改为系统级 systemd 服务（由 systemd 直接管理，不在 cron cgroup 内，
并可在发行版启动早期就拉起）：

```bash
sudo tee /etc/systemd/system/spike-hdfs-namenode.service >/dev/null <<'UNIT'
[Unit]
Description=SPIKE HDFS NameNode
After=network.target
[Service]
User=hadoop
Environment=JAVA_HOME=/home/hadoop/jdk-11
Environment=HADOOP_HOME=/usr/local/hadoop
Environment=HADOOP_CONF_DIR=/usr/local/hadoop/etc/hadoop
ExecStart=/usr/local/hadoop/bin/hdfs namenode
Restart=on-failure
RestartSec=10
[Install]
WantedBy=multi-user.target
UNIT
# DataNode / SecondaryNameNode 同理，并把 crontab 里的看门狗删掉
sudo systemctl daemon-reload && sudo systemctl enable --now spike-hdfs-namenode
```

注意：**这仍然无法让 HDFS 在发行版被 Stopped 时保持在线**，因为那是 WSL 的发行版生命周期决定的。

### 12.1 MySQL 为什么监听 3307 而不是 3306

Windows 宿主已运行 **`MySQL80`** 服务，占用 3306 与 33060；而本机 `.wslconfig` 使用
`networkingMode=Mirrored`，WSL 与 Windows **共享网络栈**，因此 WSL 内的 MySQL 无法绑定 3306
（表现为 `Bind on TCP/IP port: Address already in use`，服务反复重启失败）。

解决办法：用 drop-in 配置 `/etc/mysql/mysql.conf.d/zz-spike.cnf` 把端口改为 **3307 / 33061**，
**没有改动** `/etc/mysql/mysql.conf.d/mysqld.cnf` 主配置，也**没有触碰** Windows 的 MySQL80。

> 若哪天想让 WSL 内 MySQL 回到 3306：停掉 Windows 的 MySQL80，或把 `.wslconfig` 的
> `networkingMode` 改回默认 NAT，然后删除 `zz-spike.cnf` 并 `systemctl restart mysql`。

## 13. Python 3.14 → 3.11 迁移（2026-11-02，§12.4 的预警应验）

### 13.1 故障现象

复验环境时，PySpark **任何作业都跑不起来**，连最小的都不行：

```
>>> spark.sparkContext.parallelize(range(10)).count()
RecursionError: Stack overflow (used 8156 kB) while calling a Python object
  cloudpickle/cloudpickle.py: _should_pickle_by_reference
                          -> _lookup_module_and_qualname
Normalization failed: type=AttributeError
when serializing function reconstructor
when serializing function object ...
```

注意 `SparkSession` 能正常创建，只有**提交作业**时才崩——因为提交时会用 cloudpickle
序列化闭包，而 PySpark 3.5.3 内置的 cloudpickle 在 Python 3.14 上会无限递归。

### 13.2 版本依据

| PySpark | 官方支持的 Python |
|---|---|
| 3.5.3 / 3.5.9 | 3.8 – 3.11 |
| 4.0.5 | 3.9 – 3.13 |
| 4.3.0 | 3.11 – 3.14 |

而 Ubuntu 26.04 系统 Python 是 3.14.4，apt 源里**没有** 3.11/3.12/3.13。

### 13.3 为什么不能卸载系统 Python 3.14

`apt-get -s remove python3.14` 模拟结果显示会连带删除 **118 个包**，其中包括：

- `ubuntu-minimal`、`ubuntu-wsl`、`wsl-setup`（WSL 集成）
- `sudo-rs`（sudo 本身）
- `netplan.io`、`networkd-dispatcher`（网络）
- `cloud-init`、`npm`、`python3-venv`

等于把整个发行版拆掉。**系统 3.14 必须保留。**

### 13.4 采用的方案

用 `uv` 装一个**独立**的 CPython 3.11.18（装在 `~/.local/share/uv/python/`，不碰系统），
项目 venv 建在它之上：

```bash
python3 -m pip install --user --break-system-packages uv
uv python install 3.11
uv venv --python 3.11 /home/hadoop/spike-venv
# 注意：pyspark wheel 有 317MB，pip 缓存里已有，
# 直接指定本地 wheel 安装可免去重复下载
pip install /home/hadoop/.cache/pip/wheels/*/*/*/*/pyspark-3.5.3-*.whl
pip install pandas numpy pyarrow flask flask-cors pymysql cryptography pyyaml requests
```

结果：`/home/hadoop/spike-venv` = Python 3.11.18 + pyspark 3.5.3，系统 `python3` 仍是 3.14，
两者互不影响。旧 venv 备份在 `/home/hadoop/spike-venv-py314-backup`。

### 13.5 顺带踩到的两个新坑

1. **`uv` 不读 pip 缓存**。用 `uv pip install pyspark` 会重新下载 317MB，
   实测 10 分钟才下到 40%（约 300 KB/s）。改用 `pip` 并显式指定缓存里的 wheel 后，
   几秒钟装完。**结论：本机装大包优先用 pip（缓存已满），uv 只用来管 Python 解释器和建 venv。**
2. **Spark 默认开启分区列类型推断**。`partitionBy("product_id")` 写入时是 string，
   读回时纯数字的 `100012043978` 会被推断成 `bigint`。
   取分区值比较时必须 `str()` 转换，否则断言会莫名失败。
